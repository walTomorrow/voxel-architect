# Voxel Architect — Vision & System Design

## Overview

Voxel Architect is a conversational AI system for creating editable, constraint-aware voxel architecture from text prompts, reference images, and iterative user feedback.

The project is inspired by Minecraft-style building, but its core goal is broader: to explore how AI can translate human architectural intent into structured, deterministic, buildable voxel designs.

Voxel Architect is being built as a Stanford CS 153: Frontier Systems project.

---

## Product Vision

Voxel Architect lets a user describe or show a building idea, receive an interactive 3D voxel build, and refine it through conversation and direct spatial selection.

Example interactions:

- “Build a cozy mountain cabin from this image.”
- “Make the roof steeper and add a chimney.”
- “Change the exterior palette to match these reference colors.”
- “Make this selected upstairs area a bedroom.”
- “Add another floor in the same style.”
- “Approximate this cathedral as a voxel build, but keep it small enough for survival-mode Minecraft.”

The system is not intended to perform perfect 3D reconstruction from images. Instead, it acts as an intelligent architectural translation system between:

- text prompts
- visual references
- architectural features
- semantic building plans
- deterministic voxel generation
- interactive 3D refinement

The user experience should feel like working with an AI architectural assistant, not like writing block coordinates.

---

## First-Principles Mental Model

Voxel Architect should work like a semantic design compiler.

```text
user text/images/selection
  → AI interpretation
  → semantic architectural blueprint
  → internal component plan
  → deterministic component generators
  → validated VoxelBlock[]
  → 3D render and iterative editing
```

The AI acts as the architect and editor. It reasons about intent, proportion, style, visible features, likely interior use, and requested changes.

The deterministic generator acts as the builder/compiler. It decides exact voxel coordinates, resolves conflicts, enforces constraints, and emits the final block structure.

The AI should normally say:

```text
add a second floor, place a large front window, make this zone a bedroom, use a rustic palette
```

It should not normally say:

```text
place block A at x=1, y=2, z=3
```

Raw voxel placement is generated by code, not authored directly by the model.

## User Workflow

A typical long-term workflow looks like this:

1. The user provides text and/or images.
2. The AI interprets the request semantically: building type, style, massing, visible features, approximate proportions, interior hints, and constraints.
3. The system creates or updates a structured architectural blueprint.
4. The blueprint compiles into an internal component plan.
5. Component generators create walls, roofs, windows, doors, chimneys, furniture zones, stairs, and other architectural elements.
6. The renderer shows one or more 3D views of the build.
7. The user refines the design by chatting, uploading more images, changing materials, or selecting a region of the 3D build.
8. The AI edits the semantic plan, and the deterministic generator recompiles the build.

This loop is the product: conversational architectural iteration over structured, testable voxel generation.

## Core Product Principles

### 1. Semantic First

The main authoring surface is semantic architectural intent: building families, components, styles, zones, constraints, and edits.

Voxel blocks are compiled output.

### 2. Deterministic Generation

AI models should interpret, plan, and edit. Deterministic code should generate geometry, resolve collisions, validate constraints, and produce `VoxelBlock[]`.

### 3. Components Over One-Off Generators

Building families are useful, but they should not become dozens of isolated generator implementations.

A building family should be a curated recipe over reusable architectural components.

Examples:

```text
cabin = rectangular body + pitched roof + front entrance + sparse windows + chimney + hearth zone

tavern = wider body + public common room + window band + sign marker + chimney + optional guest rooms

chapel = hall body + centered entrance + tall feature window + pitched roof + steeple + altar zone
```

### 4. Images Are Inspiration, Not Direct Reconstruction

Reference images should guide the AI toward visual features, proportions, materials, style, and likely components.

The system should not depend on pixel-perfect reconstruction. It should produce a buildable voxel interpretation.

### 5. Iteration Requires State

For the AI to make meaningful edits, it needs more than a screenshot. It should receive a compact representation of the current build: semantic blueprint, component plan, interior zones, spatial summaries, selection metadata, validation results, and canonical rendered views.

### 6. Interiors Are Semantic Zones First

Interiors should begin as zones and circulation constraints, not perfect rooms or hand-authored coordinates.

Examples:

- living space
- bedroom
- forge zone
- storage zone
- common room
- altar zone
- kitchen zone
- stairwell

The generator decides exact bounds, clear paths, furniture anchors, and voxel placement.

### 7. Reliability Is a Feature

Every generated build should pass structural checks: valid block ids, valid shapes, no duplicate occupied cells, block budget limits, grounding, connectivity, and material compatibility.

## Major Infrastructure Goals

Voxel Architect’s infrastructure should grow around a small number of durable subsystems.

### AI Interpretation Layer

Converts user text, reference images, and selected-region requests into semantic edits. It identifies building intent, style, approximate proportions, visible components, likely interior use, and constraints.

### Semantic Blueprint Layer

Stores the user-facing design intent: building family, scale, materials, style, exterior features, interior zones, and constraints. This is the stable contract between AI planning and deterministic generation.

### Architectural Component System

Defines reusable deterministic components such as wall shells, roofs, windows, doors, chimneys, porches, stairs, furniture objects, and interior zones. Components are the main building blocks of versatile generation.

### Family Recipe System

Maps recognizable building types into curated component recipes. Families such as cabin, tower, blacksmith, tavern, chapel, barn, and shopfront should be recipes over components rather than fully separate block-placement systems.

### Interior Plan System

Represents floors, zones, circulation, feature anchors, and room-like areas. It allows prompts such as “make this selected area a bedroom” or “add a living space downstairs” to become structured, valid generation requests.

### Spatial Summary System

Produces compact summaries of the current build for the AI: dimensions, floors, openings, windows, walkable areas, occupied regions, zone bounds, selected-region contents, and adjacency information.

### Multi-View Render Context

Generates canonical visual views for the AI and user: front, back, side, top-down, roof, floor cutaway, and selected-region close-ups. Rendered images help with style and visual judgment, while structured state remains the source of truth.

### Region Selection and Local Editing

Allows the user to select a 3D region and ask for semantic changes. The system should summarize the selected region, ask the AI for a structured edit, regenerate only what is needed, and preserve surrounding context when possible.

### Material and Style System

Maps visual or textual style requests into available materials and block palettes. It should support palette matching from images, style overlays, and material compatibility with partial shapes.

### Validation and Repair System

Checks generated structures and component plans before display. It should catch impossible geometry, unsupported block states, floating structures, blocked entrances, disconnected interiors, and over-budget outputs.

### Persistence and Versioning System

Stores builds as semantic plans plus generated outputs. Users should be able to revisit, branch, compare, and roll back design iterations.

### Export System

Eventually converts validated voxel builds into external formats such as Minecraft schematics or other game/environment formats.

## Rendering and Context System

The renderer should support both user visualization and AI context generation.

User-facing rendering should support:

- interactive 3D preview
- camera controls
- material grouping
- layer views
- cutaway views
- interior inspection
- selected-region visualization

AI-facing render context should support:

- front/back/left/right canonical images
- top-down roof view
- floor cutaway renders
- selected-region close-ups
- optional before/after comparison renders

Rendered images are useful for visual judgment, but structured state is the source of truth.

---

## Interior Representation

Interior generation should be based on semantic floors, zones, features, and circulation.

A useful interior plan contains:

- floors and levels
- zones such as bedroom, living space, forge, storage, common room, kitchen, altar, or stairwell
- feature requests such as bed, table, hearth, workbench, shelves, altar, counter, or lamp
- circulation constraints such as clear paths from entrance to stairs
- placement hints such as near window, against wall, back-left, upstairs, or adjacent to chimney

The AI may propose interior intent. Deterministic code should allocate bounds, reserve paths, place furniture, and emit voxel blocks.

## Development Philosophy

### Build Vertical Slices

Prefer complete loops over isolated infrastructure.

A good slice looks like:

```text
semantic request → validated plan → deterministic generation → render → edit path
```

### Keep the AI Boundary Clear

AI should produce structured intent and edits. Code should produce geometry.

### Preserve Testability

Generation should remain deterministic enough to test with hard invariants and behavior-focused tests.

### Avoid Premature Generality

The component system should grow from real reusable architectural needs, not from an overly broad abstract graph on day one.

### Prefer Useful Approximation

The product should explain simplifications and produce buildable voxel interpretations rather than chasing perfect reconstruction.

---

## MVP Direction

The MVP should prove the core loop:

1. semantic building intent
2. deterministic voxel generation
3. 3D preview
4. conversational or UI-driven refinement
5. validation-backed reliability

Near-term implementation should prioritize:

- a reusable architectural component grammar
- family recipes over components
- semantic interior-zone schemas
- canonical render views and cutaways
- compact spatial summaries for future AI agents
- selected-region metadata for local edits
- style/material mapping that can later accept image-derived palettes

Advanced features such as full image-to-building agents, public component blueprint editing, rich room planning, Minecraft export, and collaborative multi-user workflows can build on top of this foundation.

## Current Development Status

Implementation evolves on active Git branches; treat the repository as the source of truth for live branch names and exact shipped features.

As of this vision revision, the project has established:

- deterministic voxel rendering and preview infrastructure
- semantic blueprint-driven generation for shipped families
- multiple generator families as early proof points
- partial block support including cubes, slabs, panes, and posts
- material metadata and material compatibility helpers
- generator reliability tests and structural invariants
- a clear AI/code boundary: AI plans, deterministic code places blocks

The current architectural pivot is to move from family-specific generators toward reusable architectural components and internal component plans. Future work should connect those component plans to AI interpretation, interiors, multi-view render context, and iterative editing.
